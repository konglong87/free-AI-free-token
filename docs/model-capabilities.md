# 模型能力标签

首页先展示供应商的能力概览，再按能力分组列出代表性模型。标签仅汇总仓库已收录的免费模型，不代表平台全部能力，也不保证免费政策长期不变。

## 统一标签

| 标签 | 输入 → 输出 | 用途 |
| --- | --- | --- |
| 📝 文本生成 | 文本 → 文本 | 对话、写作、代码、推理等文本输出 |
| 👁 图片理解 | 图片（可附文字）→ 文本 | 看图问答、识图；不表示能生成图片 |
| 🖼 文生图 | 文本 → 图片 | 根据文字生成图片 |
| 🖼 图生图 | 图片（可附文字）→ 图片 | 根据参考图生成或修改图片 |
| 🖼 图像编辑 | 图片 + 编辑要求 → 图片 | 修改已有图片；保留来源的能力名称，不自动推断支持全部图生图功能 |
| 🎬 文生视频 | 文本 → 视频 | 根据文字生成视频 |
| 🎬 图生视频 | 图片（可附文字）→ 视频 | 使用参考图、首帧或首尾帧生成视频 |
| 🎬 视频生成 | 输入方式待细分 → 视频 | 来源仅确认视频生成时使用，不擅自补全文生视频或图生视频 |

同一模型支持多个能力时，可组合标签，例如 `文本生成 · 图片理解`、`文生图 · 图生图`。推理、代码、工具调用等更细的功能留在供应商的 `models.md`，避免首页标签过多。

## 核验边界

- **不靠模型 ID 猜能力**：名称中有 `Vision`、`Image`、`Video` 不等于已确认支持对应输入或输出。能力必须能追溯到 `providers/<slug>/models.md` 及其官方来源或实测记录。
- **理解与生成分开**：图片理解不能标为文生图；视频理解不能标为视频生成。后续确有视频理解或音频模型时，再扩充标签。
- **不确定就明确标注**：如 `图片理解（待核验）`；模型分组标题与供应商标签必须同时保留这一限定。
- **概览与模型一一对应**：左侧标签可以覆盖目录内完整清单，右侧每组只标注该组模型支持的能力；具体模型仍以目录内说明为准。
- **聚合平台不一概而论**：例如 OpenRouter 的 `*:free` 表示免费模型集合，不表示每个模型都有相同能力。首页只汇总仓库已有记录。
- **能力与免费状态独立**：供应商原有状态标记不代表所有模型、能力和客户端均已实测；限时免费、额度、接口与核验范围仍需查看详情。

## 首页排版约定

`README.md` 与 `readme-B.md` 使用相同的两列结构：

1. **供应商 · 免费能力**：名称链接到供应商目录，下面显示带文字的能力标签；不依赖远程徽章图片。
2. **代表性模型 · 接入**：按能力分组，每个模型 ID 单独一行；API、注册、完整模型和已有证据入口放在同一单元格下方。

不再为能力增加横向列，也不在表格里直接展示长 API URL。保留完整、可复制的模型 ID，不截断、不插入零宽字符。使用 GitHub 支持的基础 HTML，不依赖自定义 CSS 或脚本。

修改两份首页后，运行 `./scripts/validate-layout.sh`，并在实际浏览器里检查桌面、平板和手机宽度。验收应包括截图、表格横向溢出、模型 ID 完整性、能力与来源对应关系，以及目录、API、注册和证据链接是否保留。
